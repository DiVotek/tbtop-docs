---

Every panel page runs behind `auth:{guard}`. The package handles the parts that only make sense inside a panel:

- **Sign-out.** Every panel answers `POST {prefix}/logout`, which the user menu posts to.
- **The signed-in user.** The panel's guard user is shared as the `tbtop.user` Inertia prop, which the header's user menu reads.
- **Sign-in and password reset.** These ship as base pages. `admin:install --auth` publishes them into your app, where you own them.

The host app still owns the rest of authentication: the user model, the guard, the password broker, and anything beyond sign-in and reset. Registration, email verification and a second factor do not ship. See [What stays yours](#what-stays-yours).

## Publish the auth pages

```bash
php artisan admin:install --auth
```

This writes three files to `app/Admin/Pages/Auth/`:

| File | Path | Route name |
|---|---|---|
| `LoginPage.php` | `{prefix}/login` | `tbtop.{panel}.login-page` |
| `ForgotPasswordPage.php` | `{prefix}/forgot-password` | `tbtop.{panel}.forgot-password-page` |
| `ResetPasswordPage.php` | `{prefix}/reset-password/{token}` | `tbtop.{panel}.reset-password-page` |

Each file is an empty subclass of a package base page in `Tbtop\Admin\Auth`:

```php title="app/Admin/Pages/Auth/LoginPage.php"
<?php

namespace App\Admin\Pages\Auth;

class LoginPage extends \Tbtop\Admin\Auth\LoginPage {}
```

The behaviour lives in the base, so fixes arrive with `composer update`. The file is yours: override a hook in it to change the screen, or delete it to drop the screen. Deleting `ForgotPasswordPage` and `ResetPasswordPage` drops password reset, and the login page stops showing its "Forgot your password?" link.

How the command behaves:

- **One panel per run.** With several panels registered, pass `--panel=<id>`. With none registered, or several and no `--panel`, it refuses and changes nothing.
- **It never overwrites.** A file that already exists is reported and left alone, unless you pass `--force`.
- **It skips pages the panel already serves.** If the panel already has a page at the same path or slug, such as a login page you wrote earlier, that page is skipped. Two would break every request to the panel with a duplicate-slug error. Delete your old page first if you want the published one.
- **It prints the steps it does not do for you.** The guest redirect below, and a `discoverPages()` line when the panel does not discover `app/Admin/Pages`.

Without `--auth`, `admin:install` publishes only the root view, the JS entry and the stylesheet, as before.

<Callout type="info">
  The scaffold always writes to `app/Admin/Pages/Auth`. Running `--auth` again for a second panel reports the files as existing and does nothing. For a second panel, write its subclasses by hand in another directory.
</Callout>

## Send guests to the login page

When a guest opens a protected page, Laravel's `auth` middleware redirects to the route named `login`. Without such a route, the guest gets a 500. Point the redirect at the panel's login page:

```php title="bootstrap/app.php"
->withMiddleware(function (Middleware $middleware): void {
    $middleware->redirectGuestsTo(fn () => \Tbtop\Admin\Auth\LoginPage::url() ?? '/admin/login');
})
```

`LoginPage::url()` returns the login page of the panel the request belongs to, so one line serves every panel. Outside a panel it returns `null`, and the fallback applies. If your public site has its own `login` route, return it as the fallback instead, so site guests keep landing there:

```php
$middleware->redirectGuestsTo(fn () => \Tbtop\Admin\Auth\LoginPage::url() ?? route('login'));
```

## What the pages do

The three pages share one shell:

- **Public.** Their middleware is `['web', RedirectSignedInUsers::class]`, not the panel's stack. A guest can reach them even when the panel's stack carries an access check.
- **Signed-in users are sent into the panel.** A user already signed in on the panel's guard who opens one of them lands on the panel root. Laravel's own `guest` middleware is not used, because it redirects to the app's home route, which knows nothing about panels.
- **Never the panel home.** The panel root redirect skips auth pages, whatever order they are registered in.
- **Hidden from [MCP](/docs/integrations/mcp).** Signing in needs a browser session.
- **Chrome-less.** They use the `center` layout, and their forms skip the unsaved-changes guard.

**Sign-in** checks email and password on the panel's guard, never the app's default guard. It has a "Remember me" checkbox. Failed attempts are throttled to five a minute per email and IP address. On success it renews the session and sends the user to the page they were bounced from, or to the panel root.

**Forgot password** emails a reset link that opens the panel's reset page, not Laravel's `password.reset` route. Laravel's global `ResetPassword::createUrlUsing()` is left alone for your app's own links. The answer is the same whether or not the email is registered, so the form does not reveal which accounts exist. Requests are throttled to five a minute per IP address.

**Reset password** sets the new password, rotates the remember token so other devices with a remember cookie are signed out, and sends the user to the login page. An unknown email gets the same answer as a bad token, and failed attempts are throttled to five a minute per IP address.

The pages assume a user model with `email` and `password` columns, and the `password_reset_tokens` table from Laravel's application skeleton.

## Customize the pages

Override a hook in the published subclass. The login page has the most:

| Hook | What it controls |
|---|---|
| `view(S $s)` | The whole screen. |
| `credentials(ActionCtx $ctx)` | The array the guard's provider matches the user by, plus `password`. Defaults to email and password. |
| `afterAuthenticated(Authenticatable $user, ActionCtx $ctx)` | Runs after the session is established. Return a URL to send the user there instead of `redirectTo()`. Return `null` to carry on. |
| `redirectTo(ActionCtx $ctx)` | Where the user lands: the intended URL, else the panel root. |
| `throttleKey(ActionCtx $ctx)` | The rate-limit key. Defaults to the login value from `credentials()` plus the IP address. |
| `maxAttempts()` | Failed attempts allowed per key per minute. Defaults to 5. |
| `static middleware(PanelConfig $panel)` | The page's middleware. Extend it to add an allowlist, since the page skips the panel's stack. |

`ResetPasswordPage` adds `passwordRules()`, which defaults to `['required', 'confirmed', Password::defaults()]`. `ForgotPasswordPage` has only `view()`.

Sign in with a username instead of an email:

```php title="app/Admin/Pages/Auth/LoginPage.php"
use Tbtop\Admin\Actions\ActionCtx;

class LoginPage extends \Tbtop\Admin\Auth\LoginPage
{
    protected function credentials(ActionCtx $ctx): array
    {
        return ['username' => $ctx->form['email'], 'password' => $ctx->form['password']];
    }
}
```

The throttle key follows `credentials()`, so it changes with it.

### Add a second factor

`afterAuthenticated()` is where a second factor hooks in. Sign the user back out, remember who they are in the session, and send them to a challenge page you write as an ordinary public DSL page:

```php title="app/Admin/Pages/Auth/LoginPage.php"
use App\Models\User;
use Illuminate\Contracts\Auth\Authenticatable;
use Illuminate\Support\Facades\Auth;
use Tbtop\Admin\Actions\ActionCtx;

class LoginPage extends \Tbtop\Admin\Auth\LoginPage
{
    protected function afterAuthenticated(Authenticatable $user, ActionCtx $ctx): ?string
    {
        if (! $user instanceof User || ! $user->hasTwoFactorEnabled()) {
            return null;
        }

        Auth::guard(static::panel()->guard())->logout();
        $ctx->request->session()->put('auth.2fa.user_id', $user->getAuthIdentifier());

        return route('tbtop.admin.two-factor-challenge-page', absolute: false);
    }
}
```

The challenge page verifies the code, then loads the parked user and signs them in on the panel's guard with `Auth::guard(...)->login($user)`. The package ships no 2FA backend, so `hasTwoFactorEnabled()` and the code check are yours.

### Rebuild the screen

The security cores are protected methods: `authenticate()` on the login page, `sendLink()` on forgot password, `resetPassword()` on reset. A subclass that rebuilds `view()` calls them from its form's `onSubmit`, so throttling and session renewal stay in place:

```php title="app/Admin/Pages/Auth/LoginPage.php"
use Tbtop\Admin\Actions\ActionCtx;
use Tbtop\Admin\Dsl\Node;
use Tbtop\Admin\Dsl\S;

public function view(S $s): Node
{
    return $s->stack([
        $s->displayText('Staff sign-in')->variant('heading'),
        $s->form('login', [
            $s->text('email')->label('Work email')->required()->rules('email'),
            $s->password('password')->label('Password')->required(),
            $s->actionsRow([
                $s->action('submit')->label('Sign in')->color('primary')->submit(),
            ]),
        ])
            ->guardUnsaved(false)
            ->record(['email' => '', 'password' => ''])
            ->onSubmit(fn (ActionCtx $ctx): string => $this->authenticate($ctx)),
    ]);
}
```

To change what a core does, override it and wrap `parent::authenticate($ctx)` rather than copying it.

The pages' text comes from the `auth.login`, `auth.forgot` and `auth.reset` keys of the package's translation file. See [Interface text](/docs/getting-started/customization#interface-text) to override them.

## Choose the password broker

Reset uses the app's default password broker. A panel whose guard reads users from a different provider, such as an `admins` table, needs its own broker in `config/auth.php`. Name it on the panel:

```php
$panel->guard('admin')->passwordBroker('admins');
```

`null`, the default, uses the app's default broker.

## Sign out

The user menu's "Logout" item posts to `{prefix}/logout`, which is `/admin/logout` for a panel mounted at `admin`. The package registers this route on every panel, named `tbtop.{panel}.logout`. It signs out the panel's guard, invalidates the session, and redirects to the panel root, where the guest redirect takes the user to the login page.

If the session has already expired, the logout request fails the CSRF check with a 419. The panel answers that with the same redirect, instead of Inertia's error modal.

<Callout type="warn" title="Remove your own logout route">
  Older versions of these docs had you register `POST admin/logout` yourself. Delete that route when you upgrade. The package route now handles it on the panel's guard.
</Callout>

## The signed-in user

The package shares the panel guard's user as the `tbtop.user` prop: the model serialized with `toArray()`, or `null` for a guest. Panels with different guards each see their own user. The user menu shows `name`, and falls back to the part of `email` before the `@`.

<Callout type="warn" title="The model's serialization is the only filter">
  Whatever the model's `toArray()` returns reaches every page's HTML. The package removes nothing on top of it, so list sensitive attributes in `$hidden` (or limit the model with `$visible`).
</Callout>

The client reads the user only from `tbtop.user`. An `auth.user` prop shared from your own Inertia middleware is no longer read, so you can remove it if nothing else in your app uses it. A custom component that reads the user gets `AuthUser`, typed as `{ id: string | number; email: string; name?: string }` plus any other serialized attributes.

## What stays yours

- **Registration, email verification and a second factor.** Write them as public DSL pages. The [second factor](#add-a-second-factor) section shows where 2FA hooks in.
- **Access control.** Signing in proves who the user is, not that they belong in the admin. Limit the panel to staff with [access control](/docs/getting-started/panel#access-control).
- **An existing login screen.** If you keep a React login screen in your app's own Inertia bundle, such as a Breeze screen, skip `--auth` and end its sign-in with a full page load into the panel: return `Inertia::location('/admin')` from the controller. A plain `redirect()` is followed inside your app's bundle, which cannot render admin pages. The logout route and the shared user work either way.
